## What happened
Attack `low_memory` (low_memory): Recreate the screen several times, then squeeze memory like a low-RAM phone and come back; destroyed screens must be freed and nothing may crash.
Steps: [{"fault": "recreate_activity", "times": 3}, {"fault": "trim_memory", "level": "RUNNING_CRITICAL"}, {"fault": "trim_memory", "level": "COMPLETE"}, {"fault": "relaunch"}, {"settle": 6}]
Result: leaked: 6 destroyed Activity instance(s) still alive after a forced GC (1 -> 7): something keeps a reference to an old Activity

## Diagnosis
Root cause: MainActivity.onCreate adds `this` to the process-wide `LeakyRegistry.screens` list (MainActivity.kt:31), and nothing ever removes it. The list is a static object (MainActivity.kt:86), so each Activity instance is pinned for the life of the process. The three `recreate_activity` steps each created a new MainActivity and left the old one in the list. The forced GC therefore could not free them, which is why the count went from 1 to 7 instances, with 6 destroyed Activities still reachable.
Fix approach: Delete the `LeakyRegistry.screens.add(this)` line and the `LeakyRegistry` object. Activity instances should never be stored in statics. If something outside the Activity needs to reach it, use a lifecycle-scoped owner or a WeakReference that is cleared in onDestroy. Screen state already survives recreation through rememberSaveable and SavedStateHandle, so nothing else needs to hold the Activity.
Evidence: app/src/main/java/com/shubhasai/monkeymart/MainActivity.kt:31 - onCreate does `LeakyRegistry.screens.add(this)`, adding every Activity instance to a static list; app/src/main/java/com/shubhasai/monkeymart/MainActivity.kt:86 - `object LeakyRegistry { val screens = mutableListOf<Any>() }` is a process-lifetime holder with no removal path; app/src/main/java/com/shubhasai/monkeymart/MainActivity.kt:28-38 - MainActivity is recreated on each recreate_activity step, so each onCreate adds another instance that is never removed; Attack verdict: 'leaked: 6 destroyed Activity instance(s) still alive after a forced GC (1 -> 7)', which matches 3 recreations plus relaunch leaving old instances reachable; Checkout files (CheckoutScreen.kt, CheckoutViewModel.kt, CouponScanner.kt, OrderRepository.kt) hold no Activity reference that outlives the screen. OrderRepository keeps only applicationContext (OrderRepository.kt:23), and the ViewModel keeps only SavedStateHandle, so the registry is the cause.
