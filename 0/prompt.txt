## Diagnosis
Root cause: DealLoader.load (DetailScreen.kt:61-70) launches on GlobalScope, so the coroutine outlives the composition and the Activity. The composable passes the Activity into it (DetailScreen.kt:76, 79). When the Activity is destroyed by recreate and trim-memory, the coroutine resumes after the repository call and calls activity.supportFragmentManager.show(...) on a destroyed FragmentManager, which throws. Separately, ScreenTracker.sessionScreens (ScreenTracker.kt:9,13) is a process-wide list that keeps every Activity ever created, so destroyed screens are never freed. That matches the 'activities: 1' retained after the forced GC, and it is why the destroyed screens stay alive under memory pressure.
Fix approach: Make the load a suspend function and run it from LaunchedEffect(productId) so it is cancelled when the screen leaves composition. Have it return the product, then show the deal dialog only if the FragmentManager is still usable (or use a state flag that the composable turns into a dialog), and do not capture the Activity in a GlobalScope. In ScreenTracker, drop the list of Activity objects and keep only a counter (or hold WeakReferences), so destroyed screens can be garbage-collected.
